## Требования пользователя, которые нужно сохранить

Это небольшой внутренний Telegram Mini App офтальмологической клиники. Сценарий: создать/продолжить сессию → фото камерой или из галереи → OCR → показать фото и три редактируемых поля → подтвердить «Добавить» → сохранить в Supabase → следующая линза → завершить и скачать настоящий `.xlsx`.

Количество линз заранее не задаётся. Источник данных — текст конкретной этикетки; каталога изделий и справочника клиники нет. Пример `CNW0T2 / +20.5 D / 26187115 027` — только пример, не значения по умолчанию. Нельзя предполагать, что DataMatrix содержит модель и силу. Отдельного поля «торическая / неторическая» быть не должно.

Excel содержит ровно четыре столбца:

1. Дата сканирования.
2. Модель линзы.
3. Оптическая сила, D.
4. Серийный номер.

Одна подтверждённая линза — одна строка. SN хранится текстом, включая ведущие нули. Сила — число со знаком; ввод принимает точку и запятую. Дата — момент подтверждения сканирования, не срок годности или дата операции. Время хранится в UTC; отображение и экспорт — в часовом поясе клиники, по умолчанию `Europe/Moscow`.

## Что реализовано

- Адаптивный русскоязычный интерфейс, стартовый экран и список сессий.
- Камера/галерея через файловые поля; просмотр фотографии и распознанного текста.
- Tesseract.js в браузере, английская модель для латинских обозначений; фото не отправляется на сервер и не сохраняется.
- Эвристический разбор модели, силы рядом с D и номера после SN; неоднозначные значения оставляются пустыми. Обязательная проверка человеком.
- Сервер Express с проверкой Telegram initData (HMAC, срок 24 часа), списком разрешённых ID и проверкой владельца сессии.
- Supabase: сессии, строки линз, миграция, RLS и запрет прямого доступа anon/authenticated.
- Идемпотентное добавление по UUID; повтор после ошибки сохраняет фото и поля. Одинаковый SN в одной сессии запрещён.
- SQL-функция добавления блокирует строку сессии, чтобы согласовать добавление и завершение.
- Возобновление сессий из базы; завершённые сессии доступны для повторного скачивания.
- ExcelJS создаёт XLSX с типизированными ячейками. Экспорт читает все строки с пагинацией по 1000.
- Blob-скачивание и дополнительное сохранение через Web Share API, если доступно.

Результат 2026-11-19: 6 снимков (5 линз Alcon: Clareon, Clareon Toric, PanOptix Pro Toric; toric-01 и toric-06 — одна линза, с разметкой и без), по 7 вариантов, всего 126 полей. Новый алгоритм: верно model 19/42, power 11/42, serial 16/42; **неверно заполненных полей 0**, остальные пустые (часть с вариантами на выбор). Все 3 поля верно только в 2 из 42 прогонов. Старый алгоритм: верно 7 полей, неверно 5.
- Правки по итогам: SN без пробела `26168203001` приводится к виду 8+3 (цифры не меняются); сила без знака (`4`, `0` — обрывки текста) отбрасывается; O/0 по ширине глифа теперь проверяется и при чтении всего снимка; модель с нерешённым O/0 остаётся пустой с двумя вариантами написания.
- Поиск плашки (там же, 2026-11-19): порог синего был подогнан под один снимок (`b > 70`), а реальная плашка тёмно-синяя (B 34–87, R ≤ 20). Теперь критерий — преобладание синего и насыщенность. Габарит плашки берётся по фактическим границам пикселей, а не по моментам: белые буквы завышали толщину. Ряды силы и SN отсчитываются в длинах плашки (0,31L и 0,56L ниже центра, стабильно на всех снимках). В окне SN метка `SN` не обязательна. Чтения модели, где один знак прочитан дважды (`O0` на одном месте), отбрасываются. В правиле O/0 опорная ширина цифры берётся только по ≥ 2 цифрам, сломанные рамки не решаются.
- После этого (42 прогона): верно model 13, power 32, serial 31; **неверно 0**; все 3 поля верно в 11 прогонах из 42. Плашка находится в 40 из 42.
- Модель (там же): рамки символов от Tesseract непригодны для геометрии (рамка `W` на всё слово, `3` шириной 5 px), поэтому O/0 и «удвоенные» знаки решались по мусору. Теперь знаки плашки сегментируются самостоятельно (связные области после бинаризации, `darkComponents` в `image.js`): на всех 6 снимках ровно `#` + 6 знаков, цифра 0 — 0,57–0,58 ширины к высоте, буквы C/N — 0,70–0,77. Чтения, у которых длина не совпадает с числом знаков, отбрасываются (если сегментацию подтверждает хотя бы одно чтение). Без плашки O/0 не решается — поле пустое с вариантами. Для окна модели: 4 варианта обработки, выбранные перебором 60 настроек (40/50/60 px, красный канал и яркость, Otsu), и набор символов `#A–Z0–9`.
- Итог (42 прогона): верно model 31, power 32, serial 32; **неверно 0**; все 3 поля верно в 28 из 42 (оригиналы — 6 из 6 по модели).
- Остаётся: на toric-01 с красной разметкой в повёрнутых вариантах сегментация ломается, и среди вариантов на выбор попадает мусор (`CNWO0T2`). Пороги и параметры подобраны на тех же 6 снимках одной марки — нужна проверка на новых фото.
- Уникальность SN: сервер приводит SN к одному написанию (`normalizeSerial` в `shared/label.js`: пробелы схлопываются, 11 цифр → 8+3, цифры не меняются). Миграция `202611190002_serial_unique_ignoring_spaces.sql` заменяет `unique(session_id, serial)` на индекс по SN без пробелов и без учёта регистра. Проверено на PGlite (WASM Postgres): `26168203001` и `26168203  001` после `26168203 001` отклоняются с 23505, повтор по UUID идемпотентен. Миграция применена в Supabase (2026-11-19).

## Известные ограничения и технические нюансы

- `DEV_AUTH=true` разрешает локального пользователя только при `NODE_ENV != production` и loopback-адресе соединения. За reverse proxy такой режим опасен, поскольку прокси тоже обращается с loopback; не публикуйте его.
- Сервер слушает только `127.0.0.1`; для внешнего доступа требуется корректная схема размещения/reverse proxy.
- Приложение без Telegram по умолчанию получает отказ авторизации после подключения базы. Для локальной проверки используйте описанный dev-режим, не ослабляйте production-проверки.
- Список показывает последние 100 сессий сотрудника. Экспорт строк внутри выбранной сессии не ограничен 1000 строками.
- Неподтверждённое фото живёт только в памяти вкладки; закрытие приложения его теряет. Есть предупреждение о закрытии, но постоянного хранения черновика нет.
- OCR загружает worker/WASM/языковые данные из сети; нет проверки точности на реальных фото. HEIC не поддерживается напрямую; используются JPEG/PNG/WebP (сервер фотографий не принимает).
- Парсер эвристический, не универсальный. Неоднозначные или нестандартные поля могут требовать ручного ввода. Штрихкоды не декодируются.
- RPC может вернуть объект или массив; API нормализует результат до одной записи.
- Дата фиксируется базой при подтверждении; Excel получает календарную дату клиники, без времени.
- Web Share вызывается из пользовательского нажатия с уже подготовленным File, чтобы сохранить пользовательскую активацию браузера.

Этот файл фиксирует состояние передачи, а не утверждает готовность развёрнутого сервиса к эксплуатации.
